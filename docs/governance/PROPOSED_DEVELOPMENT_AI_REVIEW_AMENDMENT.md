# Proposed amendment for Development/Test technical review

**Status — proposed under the Standing Autonomous Development Mandate V2.** This document requests one owner decision. The existing review requirements apply until the owner adopts the amendment and the enforcement check is verified. No live setting was changed to prepare this proposal.

## Decision requested

Approve a revision-specific independent AI technical review for routine Development/Test integration on this public development repository. Retain the recorded human review for the security-owned paths in BUILD-00 §4.1 and for material changes to security semantics, enforcement, grant scope, sensitive data, recovery or review governance. Retain qualified human assessment, independent cryptographic review, PB-12 production acceptance, and the owner’s milestone acceptance. The review agent uses its own session and has read-only access to the exact Git objects. It neither edits the change nor submits a GitHub approval as a person.

The amendment would replace the universal human approval and approval-after-last-push clauses of [ADR-PB-011 A-21](../decisions/ADR-PB-011-GITHUB-ACTIONS-SECURE-DELIVERY.md) and [BUILD-00 §1](../delivery/BUILD00_REPOSITORY_PROTECTION.md) only for the routine lane. The same rules continue for human-required changes and for existing formal acceptance. BUILD-00 §4.1 path coverage and the [review and authorization workflow](REVIEW_AND_AUTHORIZATION_WORKFLOW.md) continue to apply. The personal-account repository cannot resolve the organization teams in CODEOWNERS. Keep the file and record the named security reviewer on changes it covers pending the existing Azure DevOps milestone.

## Evidence and operation

Every PR requires a PASS from the independent review agent on its current head and base. The review examines the actual diff, requirements, security contracts, tests and reproducible evidence. It authenticates repository ID, PR number, exact head and base SHAs, test-merge SHA, policy version, reviewer session identity, disposition, severities and evidence references. FAIL, BLOCKED, stale evidence, unresolved applicable findings, missing human approval where required and a mismatch in changed-path classification all prevent integration. A change to the head or base requires a fresh review record. The coordinator logs milestones and evidence in the [work-package register](WORK_PACKAGE_REGISTER.md).

Use a repository-scoped GitHub App as the expected source of the required status. Grant repository Metadata, Contents and Pull requests read and Commit statuses write. The App has no repository administration, push, merge, bypass or human review powers. It checks authenticated reviewer evidence from a separate execution context and the live PR before publishing a success only on that PR's current test-merge SHA. Refuse a test-merge SHA shared by multiple eligible PRs. Publish no reusable status on the topic head. Use trusted GitHub push metadata to establish the latest pusher. Verify the required review is from the eligible human and applies to the current head after that push. Keep the publisher and review input configuration outside PR control. Require the correct App source in GitHub. [Required status source](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging)
