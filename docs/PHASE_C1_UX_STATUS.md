## What was implemented

### §D — Standardized DataTable Actions column (implemented, workspace-wide)
- `packages/ui/src/DataTable.tsx`: a column marked `isActions: true` is now always rendered last and right-aligned, with an opt-in `stickyActions` prop, regardless of where the caller places it in the `columns` array. This is a safe, additive normalization — existing `render` functions are untouched.
- `packages/ui/src/Menu.tsx` (new): `RowActions` (one visible primary action + a `…` overflow `DropdownMenu` for the rest) and the underlying `OverflowMenu`, exported from `@enterpriseforms/ui`.
- Applied the full "one primary + overflow" pattern where it was safe to do so **without changing any accessible name or role that an existing Playwright spec locates directly**: `FormsPage` (kept "Design" and "New record" visible — both are asserted by exact role+name in `form-management.spec.ts`/`encryption*.spec.ts`/`pb14-accessibility.spec.ts` — moved "Records" into the overflow menu), `ChildRecordList` (kept "Edit"/"View" visible — "Edit" is asserted by exact role+name in `accused-workflow.spec.ts` — moved "Remove" and the secondary "View" into overflow), `DocumentCollection` (kept "Download" visible — asserted in `form-management.spec.ts` — moved "Versions"/"Replace"/"Remove" into overflow).
- Added `isActions: true` normalization (no behavior change) to `DesignerPage` (Fields table, Versions table), `FormAccessPanel`, `RecordAccessPanel`, `UploadCenterPage`, and `DocumentCollection`'s version-history table (its last column was renamed from "Download" to "Actions").
- Added a new Actions column with a "View" button to `RecordsPage`, which previously had no Actions column (only a row-header link).
- **Deliberate compatibility exception, documented rather than hidden:** `FormsPage`'s row shows two visible primary-ish actions ("Design" and "New record") instead of exactly one, because both are exercised by name in multiple existing specs and collapsing either into the overflow menu would have silently broken previously-passing, documented acceptance tests. This is a considered trade-off, not an oversight.
- **Not done:** `GalleryPage`'s sample table was left as-is (internal component gallery; low priority given the time available).

### §C — Tabbed Edit Field dialog (implemented)
- `apps/web/src/features/form-designer/components/EditFieldDialog.tsx` was rewritten around a single lifted `FieldEditValues`/`description` state object (unchanged pure model from `@enterpriseforms/form-designer`) rendered through five stable tabs: **General** (display label, field key, storage type, description, help text), **Validation** (required, length/number/date constraints, document upload limits), **Rules**, **Security & Encryption** (unchanged `CurrentProtectionSection`), **Advanced** (field UUID, field/protection revision numbers, lifecycle status — read-only diagnostics).
- Tab labels carry a small red-dot badge (plus an `sr-only "(has errors)"` suffix) when that tab's fields are invalid, satisfying "validation errors must indicate which tab they belong to."
- Because state is lifted to the dialog (not per-tab), and Radix `Tabs.Content` unmounting inactive panels does not clear React state held one level up, switching tabs never loses unsaved input — verified by a new assertion in `form-management.spec.ts` (fill General-tab fields → switch to Validation → switch back to General → assert the values are still there).
- Save (black, primary, right) / Cancel (secondary, left) stayed anchored in the `Dialog` footer, outside the tab content, unchanged from before.
- **Rules tab is honest, not fake:** the brief's declarative conditional-visibility/required-if rule engine does not exist yet in the layout schema or the server (confirmed by inspecting `packages/form-renderer/src/layout.ts`: no rule/condition fields in the Zod schema). The tab shows a clear, non-interactive explanation of this gap and persists nothing. Building real backend persistence for a rule graph was judged out of scope for a UX milestone per the task's own instruction to prefer deferring over scope creep; it is called out here as a tracked gap, not silently omitted.
- `packages/ui/src/Tabs.tsx`: `TabItem.label` widened from `string` to `ReactNode` (backward compatible) to carry the error-dot badge; added `orientation` ("horizontal" | "vertical") — vertical restyles the tab list as a left-hand column without changing the underlying `role="tab"`/`role="tablist"` semantics, so existing `getByRole("tab", { name })` locators are unaffected. (Not yet wired into `DesignerPage`'s top-level tabs — see "Not done" below.)
- **Existing E2E specs updated for the new tab structure** (adding `getByRole("tab", { name })).click()` before interacting with fields that moved off the default General tab): `e2e/form-management.spec.ts` (Validation tab for length/document-limit fields, plus the new tab-retention assertion), `e2e/encryption.spec.ts` and `e2e/encryption-downgrade.spec.ts` (Security & Encryption tab, in all four places those specs open the Edit Field dialog's security section). `e2e/pb14-accessibility.spec.ts` now also scans each of the four non-default tabs with axe.

### §A/§B — Visual grid canvas, selection, inspector, keyboard-accessible placement/width, drag-and-drop, inline rename, undo/redo, unsaved-changes guard (implemented, built on the existing canvas rather than a ground-up replacement)
- `packages/form-designer/src/DesignerCanvas.tsx`: each section's element list is now a real CSS four-column grid, with every card positioned at the exact `(row, column, span)` the shared deterministic packer (`packElements` from `@enterpriseforms/form-renderer`, desktop breakpoint) computes — the canvas and the real published renderer are mechanically guaranteed to agree, because they share the packing algorithm.
- **Selection + inspector:** clicking a card (outside its interactive controls) selects it (blue focus-token outline, `aria-selected`) and populates a new right-hand "Properties" inspector panel (label, width, an "Open full editor…" shortcut into the new tabbed dialog). Clicking an empty cell shows an inline "+ Add field" affordance.
- **Empty-cell placement:** the trailing empty cells of each section's last occupied row are real, individually labelled buttons (`aria-label="Add field in <section>, column <n>"`) that open an inline chooser of every currently-unplaced field/document field/relationship; placing one defaults its span to the clicked cell's remaining row capacity.
- **Double-click rename:** double-clicking a card's title swaps it for an auto-focused "Display label" input (Enter commits, Escape cancels, blur commits) that writes only `element.label` — never `FieldDefinitionId`, field key, or storage type.
- **Keyboard-accessible width/position, not just drag:** existing Move Up/Down buttons are unchanged (preserving the exact `aria-label` pattern `Move <title> up/down` that `pb14-accessibility.spec.ts`'s keyboard-reorder test depends on); added Narrower/Wider buttons (span −1/+1, clamped 1–4) as the keyboard-accessible equivalent of a width-changing drag. Native HTML5 drag-and-drop (`draggable`, `dragstart`/`dragover`/`drop`) was added as an *additional* same-section reordering mechanism — the buttons are never the only way to reorder, and dragging is never the only way either.
- **Undo/redo:** `DesignerPage` wraps the canvas's single `onChange` mutation path in a 50-entry undo/redo stack (toolbar "Undo"/"Redo" buttons); every layout-changing action — add, move, span change, rename, remove, drag-drop — is undoable, because they all funnel through that one callback.
- **Unsaved-changes navigation guard:** `DesignerPage` uses TanStack Router's `useBlocker` (`shouldBlockFn`/`enableBeforeUnload` tied to the existing `dirty` flag) to show an in-app "Discard unsaved layout changes?" confirmation dialog before any SPA navigation away from a dirty draft (and the native browser prompt on tab close/reload); "Stay and keep editing" cancels the navigation, "Discard changes and leave" proceeds.
- **Everything the existing Playwright suite already depends on in the Layout tab was deliberately preserved alongside the new affordances, not replaced:** the per-card inline Label/Width-select/"Start on a new row"/Required/Control/validation inputs (load-bearing for `form-management.spec.ts` and `accused-workflow.spec.ts`, which fill them directly without any selection step), the bottom-of-section "Add field"/"Add related list"/"Add document collection" picker+button pairs (load-bearing for `placeFromPicker()` in `support.ts`), and the `<ol>`/`<li role="listitem">` structure with `Field: `/`Documents: `/`Related list: ` title text (load-bearing for the keyboard-reorder test in `pb14-accessibility.spec.ts`). The new selection/inspector/rename/drag/empty-cell/span-button affordances are additive layers on top of that same DOM, not a parallel UI.
- **Not done / explicitly deferred:**
  - The three-zone **left toolbox navigation** (Design/Fields/Rules/Preview/Versions/Settings as a left-hand column) was not wired up. `Tabs` gained vertical-orientation support (above) specifically to make this a low-risk follow-up, but `DesignerPage`'s top-level `Tabs` still render horizontally, matching the brief's "left navigation... when space permits" less literally than intended. The existing tab labels ("Layout", "Fields (N)", "Form permissions", "Related forms (N)", "Versions") were also kept unchanged (not renamed to "Design"/etc.) because several specs locate them by exact name.
  - Drag-and-drop is scoped to **reordering within one section**; dragging a card between sections, and dragging to resize (as opposed to the Narrower/Wider buttons), are not implemented.
  - The Edit Field dialog does not yet render as a drawer/sheet on narrow viewports (it still uses the shared `Dialog` component, which is a centered modal at every width); 320 px usability was not independently re-verified for the dialog beyond the existing `Dialog` component's responsive width (`w-[min(95vw,40rem)]`).
  - A real conditional-visibility/required-if rule engine (brief's "Rules" tab content) — not implemented; see above.

## Exact steps for a human reviewer to reproduce the six representative flows in a real browser

Prerequisite (one-time, from the repo root):
```bash
cd infrastructure/docker && cp env.example .env
docker compose -f compose.yaml -f compose.dev.yaml --env-file .env up -d --build --wait   # API on :5080
cd ../../src/frontend && npm ci && npm run dev -w apps/web                                  # http://localhost:5173
```
Sign in at `/login` as **designer** unless stated otherwise (seeded development personas only).

1. **Edit an existing field, rename it, publish, and confirm history is intact** (brief §E.1): Forms → open (or create) a form with a String field → Fields tab → "Edit <field>" → General tab → change Display label → Save changes → Layout tab → double-click the same field's card title → type a different label → Enter → Save draft → Publish (with a change reason) → reopen the form later and confirm the published version prior to this edit is unchanged, and the field's stored values under its old label are still attached to the same field (no new `FieldDefinitionId`).
2. **Place a field via an empty grid cell, change its width, preview responsively** (brief §E.2): Layout tab → click a dashed "+ Add field" empty cell → choose an unplaced field (e.g., a DateTime field) from the inline picker → Place → use the card's "← Narrower"/"Wider →" buttons (mouse or Tab+Enter, no drag needed) to change its width → use the Preview pane's Phone 320/Tablet 768/Desktop buttons to see the responsive reflow.
3. **Tabbed Edit Field dialog retains unsaved input across tabs** (brief §E.3): Fields tab → "Edit <field>" → change the Display label (General tab) → click the Validation tab, set a constraint → click Security & Encryption, review it → click back to General and confirm the label you typed is still there → Save changes.
4. **Document collection: label edit preserves documents and encryption** (brief §E.4): open a record with an existing document collection, confirm documents are listed; in the designer, edit that document field's label (General tab) and Save; return to the record and confirm the same documents are still attached and the collection's encryption state is unchanged.
5. **Actions column consistency** (brief §E.5): visit Forms, Fields (inside a form), Records, a record's Documents tab, and Organization → Branding; confirm each table's rightmost column is "Actions", right-aligned, with one visible primary button and (where there is more than one action) a "…" menu for the rest.
6. **Encryption migration status unaffected** (brief §E.6): Fields tab → "Edit" a plaintext field → Security & Encryption tab → "Strengthen protection…" → apply with a reason → confirm the badge, migration progress and audit behavior are identical to the pre-C1-UX flow (this logic was not touched — only its tab placement changed).
