#### `InterruptedAndTamperedMigrationsNeverClaimPlaintextAndForgedCompletionIsIgnored` intermittent failure — genuine recovery defect (fixed, `a0beeea`)

- **Evidence.** On a fresh security-test stack at `2681511` the test failed in 1 of 8 isolated runs (`docs/evidence/phase-c1/2026-10-20-acceptance-prep/baseline-2681511/run-6.log`). The diagnostic added to the test showed a healthy record `Failed` after 5 attempts with `IDEMPOTENCY_CONFLICT: idempotency key reused with a different request or actor`, next to the deliberately tampered record (`DEPROTECT_AUTHENTICATION_FAILED`).
- **Root cause.** The worker derived its reprotection idempotency key (and so the authority operation id) only from (migration, record, accepted revision). When the authority is paused mid-request the worker times out and parks the migration, but the buffered `Prepare` is processed after unpause and stores a prepared operation under that key. Every retry rebuilds the candidate with fresh row identities (and, when encrypting, fresh ciphertext), so the authority correctly refuses to reuse the key; the record failed permanently. Not a harness timing problem: a real interruption (authority restart, network loss after the request is sent) produces it.
- **Fix.** The key includes the item's persisted attempt number: a crash or replay within one attempt keeps the same operation (the authority returns it, or the head has moved and the item completes as a no-op), while a new attempt gets a fresh operation and the abandoned one expires unused. `IDEMPOTENCY_CONFLICT` on a reprotection prepare is retried as the next attempt rather than counted as a record failure. No timeout or retry budget was increased; every attempt still passes the same authority Prepare/Commit rules and the content-head CAS; the tampered record still fails closed.
- **Deterministic regression (`64bed7e`).** A Testing-only, one-shot authority crash point `CrashAfterPrepareCommit` (same `IFaultInjector` mechanism and environment restriction as the SEC-P09 crash points; NoOp in every other environment) and the test `AnInterruptedPrepareNeverFailsAHealthyRecordTheNextAttemptUsesAFreshOperation`. **Revert check:** with the pre-fix worker code temporarily restored, the test failed 2 of 2 runs with exactly the field symptom (`Failed|5|IDEMPOTENCY_CONFLICT…`, `legacyPlaintextRecordCount=1`); with the fix it passes (see below).

#### `form_records.accepted_content_change_operation_id` vs. a hostile business PostgreSQL administrator (hardened, `a0beeea`, `58f0f43`)

| Question | Finding |
|---|---|
| Can it select unaccepted content for a read, projection, download or export? | **No.** The column is read only by the local legacy-plaintext/encrypted estimate in `BusinessStore`; every protected read verifies the observed rows against the authority's accepted head (VerifyRecordProjection). Test (b): a pointer aimed at a planted candidate with a different value — the record still reads the accepted value. |
| Can it bypass authority verification? | **No.** No authority call takes it as input; the reprotection worker reads the authority head for every item, and the migration post-check now counts old-form rows in the operation **the authority reports**. |
| Can it forge migration completion? | **No (fixed).** Before: the post-check verified tracked items plus the business estimate, so a record hidden from the estimate could be skipped. Now `FinalizeAsync` verifies every business record of the form against its authority head and adds any that still hold old-form rows; completion requires zero. Test (c): a consistent forgery (bogus staged header + `record_revision` + pointer) hides a record from the initial enumeration (3 of 4 enumerated) — the migration still ends with 4 of 4 records re-protected in their authority heads. |
| Can a single forged column skew the estimate? | **No (fixed).** The pointer is honoured only when a staged header of the same record with that operation exists at the projected `record_revision`; otherwise the previous rule applies. Test (a): a dangling pointer does not hide the record. The authority's commit response also replaces a stale or forged pointer at the same revision. |

**Residual (documented, not new):** the local estimate and the status flags `fullyEncrypted` / `fullyPlaintext` remain business-database projections. An administrator who writes several tables consistently (bogus headers, revisions, pointers, migration rows) can still make the *status display* wrong — exactly as before this column existed (inserting a bogus higher revision had the same effect). These flags are never used for any authorization, decryption, read or search decision. The migration post-check's record list also comes from the business database; a record removed from `form_records` is not enumerated, because the authority offers no workload enumeration of a form's records (tracked with G06).

### Integration failure fixed: `FieldProtectionDowngradeTests.CancellingAReleaseReEncryptsConvertedValuesAndRecordsTheIrreversibleExposureWindow`

Failed in both full gate runs of this round (passed in isolation). Root cause (`bddc387`): staged candidates are insert-only for the business runtime (G08). A decrypt candidate prepared just before a cancel superseded its release command is correctly refused by the authority, but its plaintext rows remain at a higher content revision than the accepted head; the business "legacy plaintext/encrypted" estimates used the highest staged revision as the record's state, so the field could never report fully encrypted again (rollback migration Completed, `legacyPlaintextRecordCount=1`). The authority behaved correctly throughout (content commits and security commands serialize on the organization row; superseded commands are refused); nothing unaccepted was ever served. Fix: `form_records.accepted_content_change_operation_id` (migration `BusinessRecordAcceptedOperation`, best-effort backfill), set on every accepted commit through `FormRecord.RecordAcceptedContent` (never moves backwards); the estimates read the accepted head's rows. The insert-only privilege is unchanged; the orphaned decrypt candidate's plaintext remains part of the Amendment A1 exposure-window residual that the test already asserts. A new deterministic regression test plants an orphan candidate through the hostile business-DBA connection.

### Two genuine Phase C1 bugs found by actually running the suite, and fixed

1. **`e2e/accused-workflow.spec.ts` locator ambiguity (test-only fix).** The new keyboard-accessible Narrower/Wider buttons' `aria-label`s ("Decrease/Increase width of Field: …") contain the substring "width", so the pre-existing `given.getByLabel("Width").click()` / `family.getByLabel("Width").click()` locators became ambiguous (Playwright strict-mode violation, 3 matches) the moment those buttons were added to the canvas card. Fixed by adding `{ exact: true }` to both call sites — the only two in the whole e2e suite that referenced "Width" loosely; everywhere else was already unambiguous (checked by grep across every spec).
2. **Inline rename didn't change what the card showed as its title, and briefly broke the card's own identity (product fix, `packages/form-designer/src/DesignerCanvas.tsx`).** Two related defects in the double-click-to-rename feature itself:
   - The card's headline (`elementTitle()`) was computed only from the **field catalog's** `fieldDisplayName`, never from `element.label` — the exact property the rename control (and the pre-existing "Label" input) writes. So renaming visibly did nothing: the "Label" input showed the new text, but the card's own title never changed, because the title was never wired to that value in the first place. `elementTitle()` now prefers `element.label` (falling back to the catalog name only when the label is blank), matching what the "Label" input, the Properties inspector and the renderer itself already treat as the field's real display text.
   - While renaming, the title `<p>` (whose text content is what every `hasText: "Field: X"` locator and sighted/AT identification of the card depends on) is swapped out for the rename `<input>`, whose *value* is not part of the DOM's text content at all — so for the duration of a rename, the card's own `hasText`-filterable identity vanished, and any locator built from the same `card` reference (exactly the pattern this feature's own test uses) could no longer find it. Fixed by adding a permanent `sr-only` identity span directly on the `<li>` (outside the part that gets swapped), computed the same way, so the card's identity is always present regardless of rename state; the redundant duplicate inside the non-renaming title was removed so screen readers don't hear it twice.
3. **Two real WCAG issues at 320 px, caught by `pb14-accessibility.spec.ts`'s axe scan once it actually ran (product fix, same file).** `aria-selected` on the card `<li>` is not a valid ARIA attribute for an implicit `listitem` role (axe `aria-allowed-attr`, critical) — changed to `aria-current`, which is a global attribute valid on any role and still announces the selected card. The Narrower/Wider/Configure buttons' visible text ("← Narrower", "Wider →", "Configure") was not contained in their accessible names ("Decrease width of …", "Increase width of …", "Open full editor for …"), violating WCAG 2.5.3 Label in Name (axe `label-content-name-mismatch`, serious) — the aria-labels were reworded to lead with their own visible word ("Narrower: decrease width of …", "Wider: increase width of …", "Configure: open full editor for …"). `e2e/designer-ux.spec.ts`'s three locators that named the old aria-label text verbatim were updated to match.

None of these three fixes touch validation/security/encryption logic, `FormVersions` immutability, field identity, or anything backend; they are confined to `DesignerCanvas.tsx` (presentation) and the two e2e spec files (test locators).
