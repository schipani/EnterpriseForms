# Stage A Decision Log

Decisions taken while implementing the Level 2 security foundation (ADR-PB-002 Stage A) where the normative documents
left a choice open or could not be applied literally. None weakens a Level 2 requirement; each states how it is revisited.

| # | Decision | Why | Revisit |
|---|---|---|---|
| A-01 | Authority PostgreSQL schema is named `authority`, not `authorization` as in the reference SQL. | `AUTHORIZATION` is a reserved word in PostgreSQL; unquoted use in grants and `FOR UPDATE` queries fails. Table and column names follow the reference exactly. | None needed; reference SQL remains the column-level source. |
| A-02 | `PrepareContentChange` carries the **full candidate snapshot as canonical RowHmac/v1 bytes** and returns authority-issued signatures; `CommitContentChange` carries the staged items **read back from BusinessDb**; the authority never connects to BusinessDb. | The authority has no network path to the business plane (stronger isolation than the reference's "authority reads back staged candidate"). The trusted business runtime pushes evidence; the authority verifies bytes, signatures, set equality and root against what it signed. | If an independent verifier worker with read-only BusinessDb access is introduced, read-back can move there. |
| A-03 | The business runtime **proposes the content operation id** (deterministic from organization, record and idempotency key); the authority enforces uniqueness and binds every signature and leaf to it. | Canonical bytes bind the operation id (replay protection, SEC-P05), so the id must be known before encoding; a two-round-trip protocol would add a window with signed-but-unbound bytes. | Server-issued ids with a two-phase prepare if independent review prefers it. |
| A-04 | Idempotent identity of a command/prepare is (organization, actor, key, canonical body **excluding `expected_authorization_revision`**); the revision stays a CAS precondition enforced separately. | A legitimate retry after the original commit necessarily observes a newer revision (SEC-P08/P09); including it made every post-commit retry an IdempotencyConflict. Content revision/root remain part of the prepare identity. | — |
| A-05 | `VerifyRecordProjection` verifies the **complete** observed set (every leaf, every signature, root) even for partial-share readers, then returns the authorized subset. The business API releases only that subset. | MRK-18 strictness; a tampered hidden row fails the whole read closed rather than risking a partial misleading response. Hidden bytes never leave the trusted business runtime. | Authority-derived expected subset without full enumeration once per-item proofs are reviewed. |
| A-06 | Effectiveness order per organization: journal commit → **archive receipt** → ordered SpiceDB projection → Effective. The gate reports `AwaitingArchive` before `AwaitingProjection`. Content reads additionally require the content checkpoint's receipt. | G14 refinement in CROSS_SYSTEM_CONSISTENCY_PROTOCOL.md; SEC-P12. | Asynchronous mode per organization policy is modelled (`checkpoint_enforcement_mode_name`) but not enabled. |
| A-07 | The archive is an **Azurite blob container on authority-net with create-only writes (If-None-Match: *)** — an explicitly labelled test double for a separately administered WORM store. No Confidential Ledger anchoring yet. | ADR-PB-003 Level A permits labelled doubles; the production archive and ledger are Azure resources (PB-10/PB-12). | Replace with Azure immutable storage + ACL in staging; G11/G14 remain open until then. |
| A-08 | Service-to-service authentication uses three distinct HS256 credentials (business workload, operator, TestIdentityProvider user assertions) validated independently by the authority; the user assertion is forwarded verbatim in `X-Delegated-User-Assertion`. | Stage A needs real authenticated calls without Entra; the authority still binds (issuer, subject) itself and never trusts a user id in JSON. Refused outside Development/Testing by startup guards. | PB-08 BFF with Entra ID and mTLS/workload identity (PB-05) before Staging. |
| A-09 | Organization bootstrap (state, identity bindings, roles, per-organization Vault key) is an **operator-plane endpoint** with its own credential, journaled as revision 1. | The reference has no provisioning command; production requires PIM/dual control, which cannot be emulated locally. | Replace with the approved provisioning workflow; keep the journal shape. |
| A-10 | Stage A command kinds: RegisterTeam, Add/RemoveTeamMember, RegisterFormDefinition, RegisterRecord, TransferOwnership, CreateShare, RevokeShare. Other reference kinds return `COMMAND_KIND_NOT_IMPLEMENTED` (422). | Invariant A7 requires explicit registration commands; the remaining kinds belong to later phases. | Add per feature with planner tests. |
| A-11 | `form_records` signed schema **v2** omits the owner projection columns; the Phase 0 v1 entry stays for conformance vectors. Staged content is immutable per operation: `form_record_revisions` + per-operation copies in `field_string_values` with a stable `field_value_item_id`. | Ownership is authority-only; signing a projection would freeze a stale value into content history. Immutable staging is required by CROSS_SYSTEM §3. | — |
| A-12 | Owner reads use `form_record#read` (= owner); recipients use `form_record#discover` + per-item `field_item#read`. No `field_item#parent_record` edges are projected in Stage A. | Keeps content-derived relationships out of the security graph; item authorization comes only from explicit share edges. | Add parent edges if item-level owner checks are needed by a feature. |
| A-13 | Pure managed gRPC stub generated from vendored authzed protos instead of the `Authzed.Net` package. | The package drags the deprecated native `Grpc.Core`, which does not fit chiseled images or PB-11 dependency hygiene. Vendored commit recorded in `VENDORED_FROM.txt`. | Re-vendor through reviewed PRs. |
| A-14 | Runtime database roles (`business_api_runtime`, `authority_runtime`) are created by cluster init scripts; EF migrations and grants run in one-shot `*-migrate` services with the admin identity; runtimes get no DDL and no DELETE on signed/journal tables. | G08 least privilege. | Azure: Entra identities, PIM/JIT migration identity (PB-05/PB-11). |
| A-15 | Crash points for SEC-P09 are **deterministic one-shot process terminations** armed through the operator plane, honoured only when `FaultInjection:Enabled` and the environment is Testing. | CONS-25 requires fault injection at named transitions; the code path is identical to production apart from the no-op injector binding. | Keep disabled outside Testing by construction. |
| A-16 | F-03 closed: JSON v1 stays integer-only; no Stage A JSONB column is signed. | row-integrity-format.md §9. | Independent review R3. |
| A-17 | `dotnet test` runs with `--minimum-expected-tests` in CI (100 for the solution, 13 for Gate A) so zero discovered tests is a failed run; `--project` is required on the .NET 10 SDK. | Requirement 8; PHASE0 Windows MAX_PATH finding. | — |
| A-18 | `security_journal_entries.journal_event_body_json` is stored as `text`, never `jsonb`; `ArchiveProcessor` recomputes `SHA-256(body)` and refuses delivery (`JOURNAL_BODY_DIGEST_MISMATCH`, organization quarantined) when it differs from `journal_event_digest`. Migration `JournalEventBodyCanonicalText`. | PostgreSQL normalizes `jsonb` (key order, whitespace, numbers), so every body read back from the store differed from the digest computed and chained at commit time; the archive stored non-canonical bytes and the Azurite 409 read-back path quarantined SEC-P12 in the clean-worktree run (finding A-F12). Evidence that cannot be re-verified against its digest must never be archived or repaired. | Confidential Ledger anchoring (G11/G14) must anchor the same digest; CONS/DR replay tests verify body ↔ digest for every archived entry. |
| A-19 | CI solution test floor is `--minimum-expected-tests 10` **per test executable** plus `scripts/ci/assert_test_totals.py` (sums the TRX files; fails below 130 executed, fewer than 4 result files, or any non-pass). Supersedes the `100` figure in A-17. | Microsoft.Testing.Platform evaluates the flag per executable; the branch CI run on Linux exited with code 9 while 133/133 tests passed. A zero-test executable still fails (requirement 8). | Raise the floors with each new test project; never lower them to make a run pass. |
| A-20 | Gate evidence is bound to the **code commit** it ran against. Documentation-only commits made after a run may sit on top of it only if `git diff <evidence-sha> <doc-sha> --stat` touches nothing outside `docs/`, `*.md`, `spec-files.json`, `SHA256SUMS.txt`; otherwise the gate must rerun. | ADR-PB-012 ties evidence to the exact source commit and image digests; status documents inevitably change after the run they describe. | PB-12 evidence register automates the diff check. |
