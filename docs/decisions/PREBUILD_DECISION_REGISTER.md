# Enterprise Forms — Pre-Build Decision Register

| Finding | Status | Decision |
|---|---|---|
| PB-01: Canonical Claude handoff | **Accepted** | One Git repository for code and normative specifications; validated completeness; see `ADR-PB-001-CANONICAL-REPOSITORY.md`. |
| PB-02: First implementation milestone | **Accepted** (Stage A: development acceptance A-23, 2026-10-18) | Security foundation (Stage A), followed by a complete Accused management vertical slice (Stage B); see `ADR-PB-002-SECURITY-FIRST-ACCUSED-VERTICAL-SLICE.md`. Stage A is ENGINEERING COMPLETE and ACCEPTED FOR CONTINUED DEVELOPMENT by the project owner; production Level 2 certification is a separate, still-open gate (independent cryptographic attestation, Managed HSM, Confidential Ledger, Azure Level B). Stage B authorized. |
| PB-03: Mandatory adversarial security proof | **Accepted** (Level A satisfied; Level B outstanding) | Two-level mandatory security validation: twelve real Docker tests before Stage B protected workflows (**passed**, SEC-P01..P12, hosted runner); real Azure staging proof and independent review before Level 2 production (**outstanding**; decision A-23 does not waive them). See `ADR-PB-003-MANDATORY-ADVERSARIAL-SECURITY-VALIDATION.md`. |
| PB-04-A1: Controlled removal of field encryption (encrypted → plaintext) | **PROPOSED — awaiting owner approval; not implemented** | Governance-approved, dual-principal, authority-commanded decryption migration with verified completion and rollback; until approved the no-downgrade enforcement stays. See `PROPOSED-ADR-PB-004-A1-ENCRYPTED-TO-PLAINTEXT-MIGRATION.md`. |
| PB-04: Encryption vs. verified search V1 | **Accepted** | Confidential encryption by default, explicitly approved Public/Internal typed plaintext search only, no encrypted-field predicate search in V1, authority-enumerated bounded completeness or fail closed. See `ADR-PB-004-ENCRYPTION-SEARCH-CAPABILITY.md`. |
| PB-05: Docker/Azure deployment baseline | **Accepted** | Docker Compose dev/integration/destructive test profiles; Azure Container Apps + Bicep; separate business/authority administration and identity; immutable image promotion across dev→staging→production. See `ADR-PB-005-DOCKER-AZURE-BICEP-DEPLOYMENT.md`. |
| PB-06: Versioned Minimal APIs and generated clients | **Accepted** | ASP.NET Core 10 Minimal APIs by vertical slice; `/api/v1`, generated OpenAPI and TypeScript clients, RFC 9457 errors, opaque cursors, ETags/`If-Match`, idempotency and durable operations. See `ADR-PB-006-VERSIONED-MINIMAL-API-CONTRACTS.md` and `docs/api/PB06_API_CONTRACT_STANDARD.md`. |
| PB-07: Prioritized request coordination and resumable uploads | **Accepted** | App-shell logical request coordinator with bounded priority lanes, dedicated Web Worker for upload/appropriate API transport, TanStack Query for independently refreshed server state, secure resumable chunks and durable .NET processing. No guarantee beyond browser/tab lifetime. See `ADR-PB-007-PRIORITIZED-REQUESTS-RESUMABLE-UPLOADS.md`, `docs/architecture/PB07_BROWSER_REQUEST_COORDINATOR_STANDARD.md` and `docs/testing/PB07_REQUEST_UPLOAD_ACCEPTANCE_TESTS.md`. |
| PB-08: Entra workforce identity and recovery | **Accepted** | Entra ID workforce first through replaceable OIDC BFF, per-provider immutable issuer/subject identity, independent org authorization, correctly configured FIDO2 policy and Conditional Access `acrs` plus freshness validation, protected tenant switching and two-person emergency recovery. See `ADR-PB-008-ENTRA-WORKFORCE-IDENTITY-FIDO2-RECOVERY.md`. |
| PB-09: Capacity, performance and recovery targets | **Accepted** | Initial target envelope: 25 organizations, 500 users/org, 500 active users overall, 100K records/org, 250 fields/form, 250 related/collection, 100 documents/record, 500 MB standard or 2 GB controlled uploads, two concurrent uploads/user, 50 API req/s sustained; p95 read <1s, write <2s, verified search <3s, card <2s, shell <2s; 99.9% monthly availability; 4h RTO, ≤15m business RPO and zero authorization rollback. See `ADR-PB-009-CAPACITY-PERFORMANCE-RECOVERY-TARGETS.md`. |
| PB-10: Canada-first data residency and privacy | **Accepted** | Customer data, backups, document storage, security journal, keys and customer-bearing logs in approved Canadian regions; Canada Central preferred primary and Canada East preferred recovery, contingent on each service’s availability/replication. Reject unapproved geographic fallback. Managed HSM Canada East extended-region restriction requires a tested Canadian-only manual DR path; PostgreSQL geo-backups alone do not prove the PB-09 15-minute RPO. See `ADR-PB-010-CANADA-FIRST-DATA-RESIDENCY.md` and `docs/privacy/PB10_CANADIAN_RESIDENCY_AND_PRIVACY_STANDARD.md`. |
| PB-11: Secure CI/CD and supply chain | **Accepted** (amended A-21, 2026-10-18) | GitHub repository (intentionally public during development; private Azure DevOps project is the deferred production source-control milestone, see ADR-PB-001/011 amendments); GitHub Actions with short-lived Entra OIDC federation; ACR; Bicep; reviewed code, reproducible scans/tests, SBOM, signed OCI digest/provenance verification and immutable image promotion; **independently approved, separately permissioned Trust Authority deployments** and security gates. See `ADR-PB-011-GITHUB-ACTIONS-SECURE-DELIVERY.md` and `docs/delivery/PB11_CICD_SUPPLY_CHAIN_RELEASE_STANDARD.md`. |
| PB-12: Release evidence and independent governance | **Accepted** | Machine-readable requirement→test→result→artifact→image→environment traceability; independent Level 2 Security Owner sign-off and separate Authority deployment approval; Canadian-region immutable retention with approved policy; noncritical time-limited exceptions only; mandatory security proof cannot be waived. See `ADR-PB-012-SECURITY-EVIDENCE-RELEASE-GOVERNANCE.md`, `docs/governance/PB12_SECURITY_EVIDENCE_RELEASE_STANDARD.md`. |
| PB-13: Import, export and organization offboarding | **Accepted** | First production release requires controlled CSV/JSON import with dry-run mapping, authorized full-fidelity portable export and independently approved tenant offboarding; uphold Trust Authority permissions, scanning/encryption, version history, audit, legal holds and Canada-first residency. Advanced integration/synchronization deferred. Implement after PB-02 Stage A/B, before real tenant onboarding. See `ADR-PB-013-IMPORT-EXPORT-TENANT-OFFBOARDING.md`. |
| PB-14: Design system / representative screen validation | **Accepted** | Approved responsive enterprise visual system with default black primary buttons, accessible organization themes/logo/text size, internal component gallery PG-069, three functional representative flows (dashboard, Accused with addresses/docs/upload, form designer), WCAG 2.2 AA target including manual assistive technology review, and independent product approval before implementing remaining screens at scale. See `ADR-PB-014-ENTERPRISE-UI-DESIGN-VALIDATION.md` and `docs/ui/PB14_ENTERPRISE_DESIGN_VALIDATION_STANDARD.md`. |
| Major decision A: Encryption vs. search | **Accepted** | ADR-PB-004; no Confidential/Restricted field-value search in V1 and no unapproved blind indexes. |
| Major decision B: Prove security architecture | **Accepted** | Mandatory executable local and cloud adversarial security evidence under ADR-PB-003. |
| Major decision C: Data residency | **Accepted** | ADR-PB-010: Canadian primary/customer data and backups, approved Canadian recovery regions, per-service replica checks and privacy review; no silent out-of-country fallback. |
