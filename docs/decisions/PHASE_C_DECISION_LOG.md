| C-05 | **Dropdown and multi-select storage (Phase C2, priority 1).** A dropdown stays the `Option` storage type; its **selection mode is a permanent field property** (`Single` / `Multiple`, `field_definitions.option_selection_mode`) so a published control and the rows already stored can never disagree. A multi-select stores **one typed row per selected option** (`field_option_values`, or one `field_encrypted_values` ciphertext row per option when the field is application-encrypted); the wire value is the option keys joined by comma (keys are snake_case, so unambiguous). Each row keeps its own `field_value_item_id`, so Merkle leaves, row HMACs and field-scoped shares work unchanged. The occurrence unique index of the option and encrypted value tables now includes the item id (and option membership has its own unique index); single-select cardinality is enforced by the write path. A share of a multi-select field shares every current selection (**Authority change:** the share planner and the partial-read verifier now treat plaintext selection leaves like value leaves; previously a plaintext dropdown could not be shared at all — fail-closed); a field-scoped **contributor may not change a multi-selection** (adding or removing rows needs record ownership). **Finding (pre-existing, not changed here):** the authority classifies a candidate item as unchanged only when its canonical bytes are identical, and those bytes bind the row key and the content-change operation id; every candidate re-signs every leaf, so **no field-scoped contributor/manager write can currently pass the authority** (`mutation exceeds the actor's edit scope`) — Contributor shares are effectively read-only until a stable-digest rule exists. This phase therefore adds no contributor-write behavior and tests only that such writes are refused. | Migration `PhaseC2OptionListsAndSelectionMode`; `CandidateBuilder.ApplyValuesDetailed`; tests `MultiSelect…`, `EncryptedMultiSelect…`, `DropdownTests`. Residual: the DB cannot enforce "one row" for single-select on the encrypted table (it is the application, as for every other typed rule). |
| C-06 | **Option catalog, snapshots and shared lists.** Options keep a permanent id and key independent of the label and are never deleted (deactivate/reactivate, relabel, reorder — audited as `FIELD_OPTIONS_CHANGED`). A published version carries a **snapshot of each dropdown's options** (id, key, label, order, availability at publish) and its **default selection** (`defaultOptionKeys`, validated: active options of the field, one for a single-select). The data-entry form uses the snapshot for labels and order and the **live catalog for availability**: deactivation applies immediately, additions and relabels reach the form on the next publish. A stored selection that is no longer selectable stays visible marked “no longer available” and **blocks a save that still contains it** until replaced (nothing is cleared or remapped). Defaults pre-fill new records in the client only; the server validates what is submitted. **Reusable lists** (`option_lists`, `option_list_items`, tenant-scoped, revision-guarded) are templates: binding one to a field **copies** its items into the field's own options (so published versions and stored values never depend on later list edits); a designer pulls list changes in with an explicit **Sync from list** (adds new items, follows labels, deactivates what the list deactivated, never reactivates, never changes keys or ids); a list-managed option's label can only change in the list. | `FormDesignerHandlers.UpdateOptionsAsync` / `SyncOptionsFromListAsync`, `OptionListHandlers`; `DropdownTests`. |
| C-07 | **Declarative conditional rules (Phase C2).** A rule is a JSON condition tree (`and` / `or` / `not`; `equals`, `notEquals`, `contains`, `greaterThan`, `lessThan`, `in`, `notIn`, `isEmpty`, `isNotEmpty`) over **stable field ids** — no expressions, scripts, SQL or URLs. Limits: depth 4, 25 nodes, 10 children, 50 set values. Operators are limited to what the source type supports (e.g. ordering only for Integer/Decimal/Date/DateTime; `contains` for text and multi-select; File fields cannot be sources); operands are validated against the source type and option catalog. Layout properties (all omitted from the stored JSON when default, so existing versions serialize byte-for-byte as before): `visibleWhen`, `requiredWhen`, `clearWhenHidden`, `showInForm`, `readOnly`. **Circular dependencies, self-references, unknown/unplaced sources and inconsistent combinations are rejected when the draft is saved and again at publish** (`FormRules.ValidateLayout`). A field hidden by a rule counts as empty for the rules that read it. The same tree is evaluated by the server (authoritative) and the renderer; the **shared vectors** `packages/form-renderer/src/rule-vectors.json` (51 cases + 10 invalid conditions) are executed by both implementations. | `FormRules.cs`, `rules.ts`, `rule-vectors.json`; `PhaseC2RulesAndOptionsTests`, `RulesTests`. |
| C-08 | **Server-side enforcement and hidden-value policy.** On every record write for a **full-scope (owner) write**: (a) conditional rules are evaluated on the *resulting* values; (b) a field hidden by a rule **cannot be changed** (set, changed or cleared) — `FIELD_HIDDEN_BY_RULE` 422; its stored value is **retained by default** (still ciphertext if encrypted, still returned only to principals authorized for it, never shown by the client); it is removed only when the designer opted in with `clearWhenHidden`, which is audited (`clearedByRule`); (c) a visible field that is required — statically or by a required-if rule — must have a value; a statically required field is not required while a rule hides it. **A field-scoped (partial) write evaluates no rules and learns nothing about them**: it cannot see the fields a rule may read; the authorized projection strips every rule property, and the client skips rule evaluation for a partial view. | `CandidateBuilder`, `AuthorizedLayout`; tests `AFieldHiddenByARuleCannotBeChanged…`, `ClearWhenHidden…`, `APartialProjectionNeverShipsRuleMetadata…`, `HiddenValuesAreRetained…`. |
| C-09 | **Read-only and Show in form.** `readOnly` is enforced by the server on every **user** write: a change or a clear is refused (`FIELD_READ_ONLY`, 403), an unchanged value is accepted (the edit form always resubmits it), and on create the only accepted value is the configured default — a read-only dropdown with a default **receives it from the server** even if the client omitted it. A read-only field that is required (or required-if) must be a dropdown with a default, otherwise nobody could ever fill it. Separately authorized **system operations** are expressed as `RecordWriteOrigin.System` (not reachable from any public endpoint; governed imports and migrations clone/rewrite rows without going through user validation) and are not bound by read-only; hidden-by-rule still protects them from silent change only for users. **`showInForm` is presentation only**: it removes the field from the *data-entry* form (create/edit), never from the authorized record view or any API response, never changes authorization in either direction (an authorized API client may still read and write it, an unauthorized one still cannot), and cannot be combined with required/required-if (the user could never satisfy it). | `ReadOnlyFieldsRejectUserChanges…`, `ShowInFormIsPresentationOnly…`, `RulesTests`. |

| C-15 | **Repeating groups: storage and identity, no trust-boundary change (Phase C3).** A section with "Allow multiple entries" places a **repeating group** (`group_definitions`: stable `GroupDefinitionId`, permanent `GroupKey` per form, insert-only for the runtime role). Each entry is a staged, signed business row in `form_record_group_revisions` whose canonical entity kind is `form_record_groups` (registered business signed schema **`form_record_groups` v1**: operation, record, group definition, signed `group_sort_order`, nullable parent occurrence, tenant). Its stable **`FormRecordGroupId` is the Merkle `RepeatedGroup` (kind 2) item id**; values inside an entry are the existing typed rows with `form_record_group_id` (already a signed column). **No change to the Authorization Authority, its command protocol, RowHmac v1 or Merkle v1**: the authority already accepted `RepeatedGroup` items of entity kind `form_record_groups`, verifies the complete leaf index (so reordering, moving a value between entries, inserting or deleting an entry directly in PostgreSQL fails closed) and its reprotection rules accept same-row copies of entry rows. | `docs/architecture/PHASE_C3_REPEATING_GROUPS_AND_DEPENDENT_DROPDOWNS.md`; migration `PhaseC3RepeatingGroups`; `BusinessSignedSchemas.FormRecordGroupsV1`; tests `OccurrenceRowsAreSigned…`, `RepeatingGroupsTests.TamperingWithEntriesIsDetected…`. |
| C-16 | **Field membership is permanent; placement rules and limits.** `field_definitions.group_definition_id` is set when the field is created (from the repeating section's "+ Add Field" cell) and never changes, so no version can reinterpret record-level values as per-entry values or back. Layout validation (draft save and publish): a group is placed by at most one section and must belong to the form; a repeating section holds only data fields of its group (no document collections, related-form lists or record-level fields); grouped fields are placed only in their section. Section `repeat` settings: `minOccurrences` 0–50, `maxOccurrences` 1–50, `allowAdd` / `allowRemove` / `allowReorder`; when entries cannot be added the minimum must be ≥ 1 (that many are created with the record). V1 has **no nested groups** and at most 50 entries per section; a candidate over the authority's 500-item ceiling is refused up front (`RECORD_TOO_LARGE`). "Allow multiple entries" can be switched on or off only while a section is empty; an unplaced group can be reused (its stored entries reappear). | `FormRules.ValidateGroups`, `FormLayoutCodec.ParseRepeat`, `FormDesignerHandlers.CreateGroupAsync` / `AddFieldAsync`, `layoutEdits.setSectionRepeat` / `sameScope`. |
| C-17 | **Entries are not field-shareable in V1.** The authority authorizes value and selection leaves for partial reads, never `RepeatedGroup` leaves; sharing a field of a repeating section would release values without their entry structure. Rather than change the authority, **share creation refuses such fields** (`FIELD_IN_REPEATING_GROUP`, 422), the share dialog does not offer them, and a partial (shared) projection drops repeating sections and never returns entry values or entry lists (defence in depth even if a share named such a field). Record-level fields of the same record remain shareable. Extending share scopes to entries is an Authority change and is **deferred for review**. | `CreateShareHandler`, `GetRecordProjectionHandler.AuthorizedLayout`, `VerifiedRecord.ToValueResponses`; tests `TamperingWithEntriesIsDetectedAndEntryFieldsCannotBeShared`, e2e share-dialog check. |
| C-18 | **Server-authoritative entry writes.** Create/update/child-create accept `groups: [{ groupKey, occurrences: [{ formRecordGroupId?, values }] }]`; for each section named, the list is the **complete new entry list in display order** (listed ids kept — their omitted field keys unchanged — entries without an id are new, omitted ids removed); sections not named are unchanged. Refused: unknown or repeated sections, forged/foreign/duplicated entry ids (`OCCURRENCE_UNKNOWN`), grouped fields sent as record values or in another section's entry, adding/removing/reordering against the section's settings (`GROUP_ADD_NOT_ALLOWED`, `GROUP_REMOVE_NOT_ALLOWED`, `GROUP_REORDER_NOT_ALLOWED`), counts outside the bounds when the list is created or changed (`GROUP_OCCURRENCE_COUNT`; a bound tightened by a later version is enforced when the entries are next changed), and any entry change by a field-scoped writer. Rules are evaluated **per entry** on the record's values plus the entry's own (a rule inside an entry may read its own section or record-level fields; a record-level rule cannot read entry fields); hidden, clear-when-hidden, required, required-if and read-only (a new entry receives read-only defaults) apply per entry, and errors name the entry path (`people[2].person_name`). Optimistic concurrency is unchanged (expected content revision, 409). Audit metadata lists entries added/removed/reordered by id and count, never values. | `CandidateBuilder.ApplyValuesDetailed` (`GroupInput`), `RecordGroupWrites`; `PhaseC3RepeatingGroupsTests` (unit) and `RepeatingGroupsTests` (real stack). |
| C-19 | **Dependent dropdowns.** A dropdown element may carry `optionFilter: { parentFieldDefinitionId, parentOptionKeysByOption }`, mapping each child option **key** to the parent option keys that allow it (keys are the immutable identifiers; labels can change freely); an option without an entry is available whatever the parent's value; single- and multi-select parents and children are supported. Validation at draft save and publish: the child is a dropdown, the parent a placed dropdown in the same entry scope or at record level, not itself, every mapped key exists in both catalogs, and **no chain loops back** (`circular dropdown dependency`). On save the server **refuses** a selection the parent does not allow (`DEPENDENT_OPTION_INVALID`, 422, naming each field path) and **never clears anything silently** — a combination made invalid by a later version must be fixed before the record can be saved, like a deactivated option. In the form, changing a parent **clears dependent selections that no longer fit, down the chain, and announces it** (polite live region); a stored invalid selection stays visible, marked as not available, until changed. | `FormRules.ValidateOptionFilters` / `DependentOptionViolation`, `options.ts` (`dependentChoicesFor`, `cascadeDependentClears`), `RulesTab` "Dependent choices"; tests in `PhaseC3RepeatingGroupsTests`, `groups.test.ts`, `RepeatingGroupsTests.DependentDropdowns…`, `repeating-groups.spec.ts`. |
| C-20 | **Encryption, documents and migrations carry entries.** Per-entry values are protected exactly like record-level values (AES-GCM per value, AAD binds tenant/record/field/item; the entry id is a signed column of the value row). Every path that rebuilds a candidate — document commit, document removal and the field-protection migration worker — now carries entry rows forward as same-row copies, so committing a document or re-encrypting a field never drops entries. | `UploadSessionHandlers`, `DocumentHandlers`, `FieldProtectionMigrationService`, `CandidateBuilder.CloneOccurrence`; tests `EncryptedFieldsInsideEntriesAreSealedPerOccurrence`, `EntriesKeepStableIdentities…`. |
