# Stage B Decision Log — Accused Vertical Slice

Decisions taken while implementing ADR-PB-002 Stage B (working Accused + AccusedAddress + document workflow) where the
normative documents left a choice open or could not be applied literally under the Stage A Level 2 foundation. None
weakens a Level 2 control; each states how it is revisited. Stage A decisions A-01..A-22 remain in force.

| B-22 | **Editing an existing field (owner acceptance defect 1).** A field has a *permanent identity* (id, key, storage type, classification) and *editable presentation*. Catalog metadata (`field_display_name`, `field_description`) is edited with `PATCH /form-definitions/{id}/fields/{fieldId}` (design permission required, `expectedFieldRevision` CAS, audited as `FIELD_CONFIGURATION_CHANGED`); the request may restate the key/type only so the server can refuse a different one with `FIELD_KEY_IMMUTABLE` / `FIELD_TYPE_IMMUTABLE` and an explanation (stored values would be reinterpreted; add a new field and migrate deliberately). Per-version presentation — label, help text, required, validation, document-collection limits — is edited in the **layout draft** through the Edit Field dialog (saved with the draft revision CAS, repeatedly), so published versions stay immutable and change only when the draft is published as the next version. Publish snapshots the catalog name into any element without its own label, so a later catalog rename never alters a published version. Values and attachments reference the field id, so renaming a File field keeps its document collection and every attachment. Layout validation now refuses rules that do not fit the storage type (length/pattern on non-String, min/max on non-numbers, dates on non-dates, lower bound above upper bound) instead of silently ignoring them. Runtime database role gets a **column-level** `UPDATE` only on `field_display_name`, `field_description`, `field_definition_revision`, `modified_on`, `modified_by_user_id` of the otherwise insert-only `field_definitions`; key, type and id remain unwritable by the runtime role. | CLAUDE.md §1/§2.2 (stable `FieldDefinitionId`, immutable storage type, immutable published snapshots, re-adding a field keeps its identity); G08 least privilege. | Explicit key/type migration workflow (new field + audited value migration); field deprecate/retire; options editor UI (API exists). |
| B-23 | **Form permissions after creation (owner acceptance defect 2).** "May create records" is the authority's `form_user` relation; it was only settable inside `RegisterFormDefinition`. New authority command kind `UpdateFormUsers` (delta: grant/revoke users and teams) is validated against the authority's own desired state — actor must hold design permission on that form (designer edge, directly or via team) or be an organization owner/system administrator; principals must be enabled bindings or active teams; duplicates, contradictions, unknown principals and empty changes are refused; only `form_user` edges are touched, never designer, owner, share or organization edges, so a change grants or removes **no** access to any record and needs **no** form version. New authority read `GET /internal/v1/form-definitions/{org}/{form}/access` returns the desired-state designers and form users only behind the open organization gate (fail-closed while archive/projection lag or quarantine), to designers/administrators only, with the same answer for unknown and unauthorized. The business API (`GET/POST /form-definitions/{id}/access`) keeps **no copy**: reads come from the authority, writes bind the command to the authority revision, require an idempotency key and a 3–500 character reason, wait for `Effective`, are audited (`FORM_ACCESS_GRANTED/REVOKED`) and return the state read back from the authority. UI: designer page **Form permissions** tab (source badge and authorization revision, grant dialog with person/team + reason, revoke with reason, designers listed read-only, explanation that records are unaffected). `GET /teams` adds a display-only team directory for the picker. Existing authority command kinds, SpiceDB schema and gate semantics are unchanged; SEC-P01..P12 and the authority planner tests are rerun. | The authority is the source of truth for every permission (CLAUDE.md §4M/§4N); business rows must never confer or hide access. | Delegated per-form administrators separate from designers; team picker for team creation UI. |
| B-24 | **Application-level field encryption (Phase 1B).** A field whose `field_protection_mode` is `ApplicationEncrypted` stores every value occurrence in `field_encrypted_values` (RowHmac/v1 schema `field_encrypted_values` v1, signed columns: logical type, ciphertext, algorithm, auth tag, envelope version, key reference, nonce, wrapped DEK) and **never** in a plaintext typed table. Each value is sealed with AES-256-GCM under a random single-use 256-bit data key that is wrapped by the configured `IEncryptionKeyProvider` KEK (`Encryption:KeyProvider`; `LocalDevelopment` is refused outside Development/Testing by the existing startup guard, anything else is `UnavailableKeyProvider` and fails closed with `503 ENCRYPTION_UNAVAILABLE` — no plaintext fallback). The associated data binds `DynamicForms/FieldValue/v1`, envelope version, tenant, record, field, value-item id and logical type, so a ciphertext cannot be transplanted between rows; the canonical wire value (`FieldValueCodec.Format`) is what is encrypted, so every logical type (String/Integer/Decimal/Date/DateTime/Guid/Boolean/Option) keeps its type metadata without a plaintext shadow. The authority allow-lists `field_encrypted_values` as `ManifestItemKind.FieldValue`, so encrypted rows are manifest leaves like any other value: a read first verifies the authority-accepted head and every row HMAC/Merkle leaf, **then** decrypts, only for callers whose field scope the authority confirmed — a flipped ciphertext byte is caught by the manifest before decryption (`423`), an AEAD failure after it is `423 FIELD_DECRYPTION_FAILED` with a generic message. Plaintext never reaches `audit_events`, Problem Details, logs or the business database. Published versions snapshot each field's `protection` (classification + mode) in the layout JSON; the live catalog may only be *strengthened* (B-26). Field and document encryption share the single development KEK (separate AAD domains and per-value/per-document DEKs); purpose-separated production keys are a PB-05/PB-10 requirement. | CLAUDE.md §4C.3 (typed ciphertext model, AEAD with AAD, envelope encryption, no plaintext copies), ADR-PB-004 Decision 2 (encryption first), §4L (envelope columns signed). | Azure Key Vault / Managed HSM provider with purpose-separated per-organization keys, KEK rotation/rewrap job, `ApplicationEncryptedExactMatch` blind index (disabled), per-record challenge unlock (§4C.5). |
| B-25 | **Classification floor and plaintext permission are organization policy; secure defaults are the designer's starting point.** `organization_security_policies` (one row per tenant, created on first use with the documented *development default*: minimum classification `Internal`, plaintext permitted for Public/Internal, `IsUnreviewedDefault = true` until an owner saves it) is read on every field creation, by the designer route and the Stage A `POST /form-definitions` route alike (`FieldProtectionPolicy.Resolve`): Confidential/Restricted **always** require `ApplicationEncrypted` (`FIELD_PROTECTION_REQUIRED` when a request asks for plaintext), a classification below the floor is `CLASSIFICATION_BELOW_FLOOR`, plaintext for Public/Internal is `PLAINTEXT_NOT_PERMITTED` when the owner has turned it off, File fields are always encrypted, and when the caller states nothing the defaults are **String/File → Confidential + encrypted, structured types → Internal + plaintext if permitted**. The database enforces the invariant `field_classification IN ('Public','Internal') OR field_protection_mode = 'ApplicationEncrypted'`. Only the organization owner (authority `ManageOrganization`) may change the policy, with a 10–2000 character statement, a revision CAS (`POLICY_REVISION_CONFLICT`) and an `ORGANIZATION_SECURITY_POLICY_UPDATED` audit event that flags a loosening; a policy change never changes how existing fields or values are protected. The development default permits plaintext Internal fields because SEC-P01..P12 and the Stage A create route rely on plaintext `field_string_values`; the UI labels it "Development default — not yet reviewed", and a real organization's production default must be set by its owner/security owner before onboarding. | ADR-PB-004 / SECURITY_SIMPLIFICATION Decision 2 (organization floor, Confidential default for free text and documents, Public/Internal plaintext only when explicitly approved), CLAUDE.md §4C.2 (tenant minimums override weaker designer settings). | Production default and approval workflow for the policy (PB-12); per-organization encryption floor verified from the independent authority rather than the business row. |
| B-26 | **Protection is strengthened by an audited command and migrated on write; it is never weakened.** `POST /form-definitions/{id}/fields/{fieldId}/protection` (design permission, 3–500 character reason, `expectedProtectionRevision` CAS) moves a field to a higher classification and/or to `ApplicationEncrypted`; any lower target is `FIELD_PROTECTION_DOWNGRADE_REFUSED`, a no-op is `409 NO_PROTECTION_CHANGE`, and the catalog `PATCH` route ignores classification/mode entirely, so no checkbox, PATCH or republish can make an encrypted field plaintext (a downgrade would need a separately approved, audited security migration that does not exist). After strengthening, every new commit of a record writes the field as ciphertext — including the carry-forward of unchanged values, which is how legacy plaintext copies are rewritten (`CandidateBuilder` re-protects each carried value under the field's *current* mode); until a record is next saved its plaintext copy stays readable to authorized callers and is flagged `legacyPlaintext` (the Edit field dialog shows the remaining count from `GET …/protection`, `migrationState = Plaintext | EncryptionPendingRewrite | Encrypted`). Published versions keep the protection they were published with; strengthening creates no version and no draft change. There is no background re-encryption worker: it would need its own signing path through the authority (a signing oracle risk) and is deferred to the Phase 1B migration job with its own command kind. Existing File fields were set to `ApplicationEncrypted` by the `StageBFieldEncryption` migration because their bytes were already encrypted by the Documents slice. Search over Confidential/Restricted fields stays unsupported in V1 (ADR-PB-004); the designer dialog says so before the field is created. | CLAUDE.md §4C.2 (never automatically downgrade; upgrade is an explicit, audited, resumable migration that fails closed on sensitive surfaces until complete), ADR-PB-004. | Authority-signed bulk re-encryption job with progress/verification; publish-impact report showing affected record counts per protection change. |
| B-27 | **Document-encryption audit fixes (2026-10-19, internal audit `docs/security/DOCUMENT_ENCRYPTION_AUDIT.md`).** (1) **Historic document versions are released only from an authority-verified snapshot**: the download reads the complete immutable rows of the operation that holds the requested version and calls the existing `VerifyRecordProjection` with the new optional `historic_committed_operation_id`; the authority verifies them against the manifest it accepted for that operation (full read permission now, open gate, unquarantined head, revision older than the head, complete leaf set, every row HMAC, root) and, on mismatch, quarantines the record and journals an incident exactly as for the head. No new command kind, no signing path, no SpiceDB change. (2) **Staging plaintext has a bounded, confirmed lifetime**: deleting a staging object first commits an empty block list (Delete Blob alone leaves uncommitted blocks of open/cancelled uploads), permanent processing failures delete staging immediately, and `DocumentProcessingService.SweepStagingAsync` (every 30 s in the worker and the in-process host) expires open/received sessions past their 24-hour lifetime (`Expired`, job `Failed`, audit event) and purges every expired or terminal session after a 2-minute grace, stamping `upload_sessions.staging_object_purged_on` (migration `StageBStagingPurge`); storage errors are retried. (3) Chunk upload and completion refuse an expired session (`409 UPLOAD_SESSION_EXPIRED`). Document-byte encryption itself (per-version DEK, segmented AES-256-GCM, AAD binding, server-side decryption) was not changed. | CLAUDE.md §4A (staged uploads expire and are cleaned by a retryable job), §4C.4 (download only after authorization and integrity), §4L/§4O (every protected read verifies HMAC + manifest; business rows are untrusted). | Managed KEK, key separation and rotation, storage managed identity and lifecycle rules, retention/purge of removed and never-committed ciphertext (audit §5). |
