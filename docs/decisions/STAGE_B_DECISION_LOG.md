# Stage B Decision Log — Accused Vertical Slice

Decisions taken while implementing ADR-PB-002 Stage B (working Accused + AccusedAddress + document workflow) where the
normative documents left a choice open or could not be applied literally under the Stage A Level 2 foundation. None
weakens a Level 2 control; each states how it is revisited. Stage A decisions A-01..A-22 remain in force.

| # | Decision | Why | Revisit |
|---|---|---|---|
| B-01 | **BFF session for the browser:** the business API issues an HttpOnly, Secure (outside Development), SameSite=Lax session cookie carrying the end-user assertion inside an ASP.NET Data Protection ticket; mutations require the `X-CSRF-Token` header matching the antiforgery cookie; bearer assertions remain accepted for service tests. Provider abstraction `IUserIdentityProvider`: `DevelopmentIdentityProvider` (Development/Testing only, synthetic personas seeded by `dev-seed` through the authority operator plane; the business API never holds operator credentials) and `EntraIdProvider` (OIDC authorization-code + PKCE registration, **not operable in Stage B**: no Entra tenant, and the authority validates only the TestIdentityProvider assertion format; startup fails closed when `ProviderKind=EntraId` is configured). | PB-08 BFF architecture with no tokens in the browser; a usable local login without a production bypass (the startup guard still refuses the test provider outside Development/Testing). | PB-08 Entra integration + authority assertion validator for Entra tokens before Staging. |
| B-02 | **Typed values:** Stage B persists String, Integer, Decimal, Date, Boolean and Option field values in their own signed tables (`field_integer_values` v1, `field_decimal_values` v1, `field_date_values` v1, `field_boolean_values` v1, `field_option_values` v1 with `field_option_id`) under RowHmac/v1; DateTime, Guid and encrypted field values are not implemented in Stage B. Validation rules live in the immutable version layout JSON per field (`required`, `minLength`, `maxLength`, `pattern`, `minimum`, `maximum`, `minDate`, `maxDate`) and are enforced server-side on create/update. | CLAUDE.md §2.4 typed relational storage; authority already allow-lists these entity kinds; F-03 keeps JSON v1 integer-only so no JSONB column is signed. | Add remaining types with new registry entries and vectors. |
| B-03 | **Form Designer persistence:** `form_drafts` (one active draft per form, `draft_revision` CAS), `field_options` (stable option ids, deactivate not delete), publish creates an immutable `form_versions` row (layout schema v2 with `relatedFormList` and `documentCollection` elements), advances `current_form_version_id`, and requires `expectedDraftRevision` + `expectedCurrentVersionNumber`. Restore = new draft from an older version. Authority `design` permission (form designer edge) gates every designer write; publishing emits no authority command because Stage B forms carry no security-policy change (all fields `Internal`, documents `Confidential` by organization floor). | CLAUDE.md §2.1/§5; `PublishFormSecurityRevision` is reserved for classification/encryption-policy changes. | When a published version changes field classification or protection, route through `PublishFormSecurityRevision`. |
| B-04 | **Parent/child records within Merkle v1:** the child's signed header (`form_records` schema **v3** = v2 + `parent_form_record_id`, `form_relationship_definition_id`, `relationship_sort_order`, all nullable) binds the link; `form_record_relationships` is a local projection. The authority `RegisterRecord` payload accepts `parent_form_record_id` + `form_relationship_definition_id`; the planner requires the actor to be the parent's effective owner and adds `form_record:child#parent@form_record:parent` instead of an owner edge, so child permissions derive from the parent (`read/edit/discover/manage_access = owner + parent->…`). `UnlinkChildRecord` removes the parent edge and makes the acting user the child's owner (data preserved, no cascade delete). | `RELATED_FORM_COLLECTIONS.md` §4–5 require authority-held links and derived ownership; Merkle v2 link leaves are deferred, and a planned header schema version bump is the sanctioned way to bind new columns (row-integrity-format.md §3.1). | Manifest v2 `RelatedRecordLink` leaves (kind 7) and `Reorder/Reparent` commands. |
| B-05 | **Documents:** chunked upload sessions (`upload_sessions`, 4 MiB chunks, Azure Block Blob staged blocks in a private `upload-staging` container on Azurite locally); `complete` enqueues a durable `document_processing_jobs` row processed by a leased `BackgroundService` (hosted by the Worker image and, in Development, also by the API) that scans (`IFileMalwareScanner`: ClamAV `INSTREAM` over TCP; unavailable scanner ⇒ job stays `ScanPending`, never Ready), encrypts (AES-256-GCM, 1 MiB segments, per-version DEK wrapped by the `IEncryptionKeyProvider` KEK — Development-only local KEK provider, refused in Staging/Production), stores ciphertext in `documents`, and records `file_attachment_versions`. **Ready requires the manifest commit**: the Worker holds no end-user credential, so the signed `file_attachment_versions` leaf (Merkle kind Attachment) is committed through the user's authenticated session (`POST /upload-sessions/{id}/commit`, auto-triggered by the Upload Center when the job is `Processed`). Downloads re-verify the record projection, decrypt server-side, `Content-Disposition: attachment`, `no-store`. Replace = new version via a new session; remove = new content revision without the leaf (bytes retained). | CLAUDE.md §4A/§4C.4 and PB-07: quarantine → scan → encrypt → signed manifest; a background worker must not act as a signing oracle on a user's behalf. | Authority-issued, session-bound delegated commit grants would let the worker finish the commit without a live user; PB-10 Canadian storage; Azure Key Vault KEK. |
| B-06 | **Audit projection:** `audit_events` (local, append-only for the runtime role) records record/child/document/share/publish events with actor, UTC time, action, outcome, correlation id and sanitized metadata; it is written in the same transaction as the local projection write where one exists. It is a queryable projection only — the authority journal remains the trusted security evidence. | CLAUDE.md §4D as applied by ADR-SEC-2026-10-16-01 (`AuditEvents` is a projection); Stage B needs a record activity timeline. | Phase 1C: canonical catalog, outbox to immutable archive, SIEM. |
| B-07 | **Record discovery and lists** come from the authority (`discover` lookup); list rows show only local projection metadata (form, status, created/modified) for discoverable records and are labelled unverified; opening a record performs the full verified read. | MERKLE §3: rendering is not discovery; verifying every record for a list would be N full verifications. | G06 verified search projection. |
| B-08 | **Organization branding and text size:** `organization_brandings` (primary/secondary colour pairs, text scale, logo as a scanned PNG re-encoded server-side) validated by the shared contrast rules; user text scale in `user_ui_preferences`. Both are projections with no authorization effect. | ADR-PB-014 §2.3; CLAUDE-DESIGN §2.3. | Full §4E/§4F preferences and catalogs. |
| B-09 | **Frontend:** Vite + React 19 + TypeScript + Tailwind v4 + Radix primitives; TanStack Router/Query; `packages/work-queue` (Dedicated Web Worker coordinator with lane budgets and a main-thread adapter), `packages/upload-manager`, `packages/form-renderer`, `packages/form-designer`, `packages/ui`; features own their pages. Generated OpenAPI types wrap a coordinator-backed client; no feature calls `fetch`. | ADR-PB-006/007/014, ADR-ARCH-001 §4U.4. | — |
| B-10 | **Integration tests** run against the real Docker stack (`compose.security-test.yaml` + ClamAV) in a new `tests/integration/EnterpriseForms.StageBTests` project reusing the Stage A harness pattern; SEC-P01..P12 stay unchanged and must pass. | Requirement 9; ADR-PB-003 forbids mocked security tests as evidence. | — |
| B-11 | **No-op publish is refused:** publishing a draft whose canonical layout equals the current published version returns `409 NO_DRAFT_CHANGES`; the published `layout_json` is always the canonical serialization of the parsed draft. | Prevents accidental duplicate immutable versions from a double click; keeps version history meaningful. | A semantic publish diff (Phase 2) replaces the byte comparison. |
| B-12 | **Document commit concurrency:** a user-session commit advances the record's content revision, so the browser serializes commits per record (coordinator `resourceKey = record:<id>`) and the upload manager retries a `CONTENT_REVISION_CONFLICT` up to four times against the new head; the server keeps the conflict as a clean 409 (never merges). Reads of a record are `503` until the authority's archive receipt for the new content checkpoint lands, so the app retries only `503` reads (TanStack `retry` predicate) and integration tests wait for readability after each commit. | CONS protocol: one accepted head per record, authority-first commit; the browser must not hide a conflict by picking a winner. | Server-side merge of attachment-only commits if conflicts become frequent under PB-09 load. |
| B-13 | **Scanner verdict on rejected uploads:** a rejected upload session has no version row; its response carries `scanVerdict = Infected` or `ScanError` derived from the failure code the worker recorded from the real clamd reply (`MALWARE_DETECTED` only follows an `Infected` verdict). Nothing is synthesized for sessions the scanner never saw. | Requirement 7: never represent a scan as complete without a scanner result; the UI must still tell the user why a file was refused. | Persist signature name on the session for operator triage (not shown to end users). |
| B-14 | **Stage B integration tests run outside the solution test run:** `tests/integration/EnterpriseForms.StageBTests` is compiled by `ci.yml` but executed only by the `stage-b-integration` workflow (and locally) against the running `compose.security-test.yaml` stack with ClamAV/worker/Azurite, exactly like SEC-P01..P12 in `security-gate-a`. The browser e2e (Playwright, Vite dev server proxying to port 5180) runs in the same workflow. | A unit-test job without Docker must not report Stage B tests as failed/missing; both Docker gates share one stack definition. | Merge into one scheduled "Docker gates" workflow once runtime is acceptable. |
| B-15 | **Local user directory projection:** `users` is a display projection filled when a principal authenticates; in Development/Testing the development login additionally projects every seeded persona of the organization so pickers (form users, shares) can name people who have not signed in. The projection confers nothing — the authority binds identities and decides every grant. | The designer must be able to grant form use before the clerk's first sign-in; production gets the directory from the identity provider/authority (PB-08). | Replace with an authority- or Entra-backed directory read model. |
| B-16 | **DateTime and Guid typed values** are added as `field_date_time_values` v1 (`date_time_value` timestamptz, signed as a canonical UTC timestamp) and `field_guid_values` v1 (`guid_value` uuid) under RowHmac/v1 with their own registry entries, runtime insert-only grants and EF migration `StageBDateTimeGuidValues`. Wire format: ISO 8601 instant with an explicit offset or `Z` at second precision (sub-second input is rejected, never truncated); canonical lower-case `D` UUID, empty UUID rejected. Controls `dateTime` and `guid`; the renderer edits local wall-clock time and submits the UTC instant. Supersedes the B-02 deferral; application-encrypted values remain deferred (Phase 1B key custody). | ADR-PB-002 reconciliation item 2; CLAUDE.md §2.4; the authority already allow-listed both entity kinds. | Encrypted values after the KEK provider (Azure Key Vault/Managed HSM) exists. |
| B-17 | **Share listing** `GET /api/v1/form-records/{id}/shares` returns the local share projection (recipient, role, field keys, status, revision, timestamps) only after the authority confirms `manage_access` for the caller; everyone else receives a concealment-safe 404. The Access tab offers create (one person, role, explicit field allow-list from fields with persisted values) and revoke. Team recipients are accepted by the API but the Stage B UI only offers people. | ADR-PB-002 Stage B item 5 (authorized share, effective access verification, revocation, child-specific visibility) needs a UI path; the projection confers nothing. | Team pickers and delegation lineage views with the Teams feature. |
| B-18 | **Records list pagination** uses the authority's opaque continuation token (revision-bound: a token issued under an older authorization revision is rejected, never widened) with a "Load more" control; page size 50. Server page size is clamped to 1..100. | ADR-PB-006 cursor contract; discovery stays authority-driven (B-07). | Keyset projection for G06 verified search. |
| B-19 | **Document replace and pause/resume in the browser:** Replace starts a new upload session with `replacesFileAttachmentId` so the worker produces the next immutable version of the same attachment (B-05 server behaviour unchanged); Pause aborts the in-flight chunk and keeps the File handle and server session so Resume continues from the chunks the server holds. Cancel of a paused upload cancels the server session. | PB-07 resumable sessions; the UI previously exposed cancel/retry only. | Pause across tab closure is impossible without re-selecting the file (browser constraint, documented). |
| B-20 | **PB-14 automated design validation** runs axe-core (WCAG 2.2 AA + best-practice) and overflow checks at 320/768/1440 px and 720/320×256 px zoom equivalents on login, dashboard, records, record (details/access), Upload Center, gallery and designer, plus keyboard-only tests (skip link, tabs, dialog focus trap, designer reorder, forced colours). Human NVDA/VoiceOver/zoom/sign-off items stay PENDING in `docs/ui/PB14_MANUAL_ACCEPTANCE_CHECKLIST.md`. | ADR-PB-014 requires executed tests before broad UI rollout; automation cannot replace the human review and is not presented as doing so. | Owner review of §2 of the checklist. |
| B-21 | **Explicitly deferred from Stage B (not defects):** operable Entra ID sign-in (BFF and provider abstraction exist; Entra fails closed — PB-08 Azure staging gate, "Pilot" in ADR-PB-002), application-encrypted field values (Phase 1B), repeating groups (Phase 3; Stage B models multiplicity as child records per ADR-PB-002), trusted search (Phase 4 / G06 / ADR-PB-004), Key Vault KEK, PB-09 benchmarks. Each remains listed in `docs/STAGE_B_STATUS.md` §7 with its owning gate. | ADR-PB-002 Stage B acceptance does not require them; implementing shortcuts would weaken Level 2 controls. | Their respective gates. |
