# ADR-PB-004 Amendment A1 — Controlled Removal of Field Encryption (Encrypted → Plaintext Migration)

- **Status:** **ACCEPTED (project owner, 2026-10-19) — IMPLEMENTED on the local Docker stack and tested (decision B-29).** Proposed 2026-10-19 as `PROPOSED-ADR-PB-004-A1-…` and approved the same day with one additional requirement: an **atomic cutover barrier** so that no encrypted value can be introduced between the zero-pending verification and completion. Production use additionally requires independent cryptographic/security review, managed key custody, Azure staging proof and Level 2 approval — none of which this amendment grants (§7).
- **Amends:** `ADR-PB-004-ENCRYPTION-SEARCH-CAPABILITY.md` §"Versioning and classification changes" (downgrading was "disallowed as an ordinary Designer edit"; the exception conditions named there are now a tested protocol).
- **Related:** CLAUDE.md §4C.2 (never automatically downgrade; downward migrations require a privileged, separately approved workflow), §4L (signed rows, manifests, anti-rollback), §4M–§4O (authority-first content commits), decision B-28 (plaintext → encrypted migration), `security_hardening/SECURITY_SIMPLIFICATION_STANDARD.md` Decision 2.

## 1. Why a separate protocol

Removing encryption is the only protection change that *increases* what a database reader can learn, and it is irreversible in practice: once a plaintext row has been committed to Business PostgreSQL, write-ahead logs, backups, replicas and the immutable revision history may hold it after any later re-encryption. The protocol therefore treats encrypted → plaintext as a governance event with its own authority commands, its own evidence and a state machine that never reports success it has not verified. Nothing here grants anyone access to a record they could not already open: the same Authorization Authority decisions gate every read before, during and after a migration.

## 2. Rules and how each is enforced (as implemented)

| # | Rule | Enforcement |
|---|---|---|
| 1 | The existing plaintext → encrypted migration (B-28) and every security guarantee stay intact. | B-28 code paths are unchanged in behaviour; the same `ReprotectionRules` validate both directions (`ProtectionDirection.Encrypt` / `Decrypt`); the encrypt suite (`FieldProtectionMigrationTests`, `EncryptionTests`) and SEC-P01..P12 are rerun. |
| 2 | Declassification and encryption removal are separately authorized commands of the independent Authorization Authority. | New command kinds `UpdateMandatoryPolicy` (the authority holds the organization's plaintext policy itself) and `ReclassifyField`; `PublishFormSecurityRevision` now accepts `required_protection_mode = Standard`. All are journaled, idempotent, revision-bound security commands; the business database holds only projections. |
| 3 | Plaintext only for Public/Internal fields, and only when the organization policy explicitly allows it. | The authority's planner refuses a release unless its own `organization_protection_policies` row (written by `UpdateMandatoryPolicy`, owner or system administrator only) has `plaintext_downgrade_permitted` **and** `plaintext_internal_fields_permitted` and the target classification is at or above the policy minimum. The business API applies the same checks first (`PLAINTEXT_DOWNGRADE_NOT_PERMITTED`). Documents (File fields) can never be released. |
| 4 | Downgrades involving Confidential/Restricted data need separate governance approval and **distinct principals**. | The authority records the classification carried by every encryption requirement (`field_classification` in the `PublishFormSecurityRevision` payload; unknown counts as sensitive). For a field recorded Confidential/Restricted, a release needs an **active** `field_reclassification` resource registered by a `ReclassifyField` command (owner/administrator, approval reference 1–200 characters, target Public/Internal ≥ policy minimum), issued by a **different authority user** (compared through the identity binding's user, not only the binding row), **no older than 24 hours**, whose target equals the release classification. The reclassification is consumed by the release. |
| 5 | An ordinary Form Designer never removes encryption with a checkbox. | The designer's strengthen route still refuses every downgrade (`FIELD_PROTECTION_DOWNGRADE_REFUSED`); the three new routes require the authority's `ManageOrganization` permission on the organization (owner or system administrator) and the authority's planner refuses a designer independently (`FORBIDDEN`). The Edit field dialog offers *Remove encryption…* / *Declassify…* only to sessions with the `organization.manage` capability; the Add field dialog is unchanged. |
| 6 | Durable, resumable, audited background decryption. | `field_protection_migrations.migration_direction = Decrypt` reuses the leased worker (batches of 25, 5-minute lease, bounded attempts, `Blocked` on dependency outage, `Failed` after exhaustion, administrator retry). Per record: authority head under the command → committed rows → encrypted rows of the field decrypted and re-encoded as typed plaintext rows of the **same item identity** (self-checked by formatting them again) → ordinary prepare/stage/read-back/commit as a reprotection operation; the authority accepts only ciphertext → plaintext pairs of that field and nothing else changed (`DEPROTECT_*` refusals). Audit: `FIELD_PROTECTION_DOWNGRADED`, `FIELD_PROTECTION_MIGRATION_STARTED`, `FIELD_VALUES_DEPROTECTED` per record, `…_RECORD_FAILED`, `…_COMPLETED`/`…_FAILED`, `…_RETRIED` — never with values. |
| 7 | **Atomic cutover barrier.** | The release command is the cutover. In the same authority transaction the `field_protection_requirement` is revoked and a `field_protection_release` registered; from that revision on the authority refuses — at **Prepare and at Commit** — any user operation whose candidate carries an encrypted row of the released field (`409 FIELD_PROTECTION_CHANGED`), and symmetrically any plaintext row of a field with an active requirement. Reprotection operations are accepted only under the *current* registering command of the active requirement/release (a superseded command authorizes nothing). The business field flips to `Standard` the moment the command is Effective, so new saves and carry-forwards are plaintext; the worker converts the rest. Completion requires every item Completed **and** a recount against the authority-accepted heads finding **zero** encrypted rows of the field; since no accepted head can gain an encrypted row of the field after the cutover, the zero-pending check cannot be invalidated by a concurrent write. Race test: `ConcurrentWritesAcrossTheCutoverCannotReintroduceCiphertextAndNoEditIsLost`. |
| 8 | Authorization is preserved during the migration; mixed records are safe; no new access. | The worker holds no user permission and produces no readable output; reads of a record with a still-encrypted value stay authorized reads (the value decrypts for callers whose field scope the authority confirms); readers without a grant stay denied before, during and after (tested). No relationship edge changes in any command. |
| 9 | Immutable versions, signed integrity, authority journals and audit evidence are kept. | Published versions keep their protection snapshot (a release creates no version); every converted record is a new accepted content revision with a complete signed manifest; historic encrypted and plaintext rows stay immutable history; all commands are journaled by the authority. |
| 10 | "Fully migrated to plaintext" only from authority-verified state. | `fullyPlaintext` in `GET …/protection` is recomputed live: field `Standard`, zero encrypted rows in the latest snapshots, the latest migration a *Decrypt* one that is Completed **and** verified by the post-check against the authority heads. A forged `Completed` business row does not produce the claim (tested). The UI badge **Fully migrated to plaintext · verified** is rendered from that flag only. |
| 11 | Cancellation re-encrypts converted active values; historical exposure may be irreversible. | `POST …/protection/cancel-downgrade` (owner/administrator) issues a new `PublishFormSecurityRevision(ApplicationEncrypted)` (barrier back), marks the decrypt migration `Cancelled` (never resumed), queues a rollback `Encrypt` migration (`rollback_of_migration_id`) over every record now holding plaintext, and audits `FIELD_PROTECTION_DOWNGRADE_CANCELLED` with `exposureWindowStart/End` and the explicit statement that plaintext in historical revisions, logs, WAL and backups is not reversible. |
| 12 | The worker has no arbitrary signing authority or unrestricted plaintext access. | Unchanged B-28 model: the business runtime can only submit revision-bound reprotection operations under an Effective command; the authority signs nothing on request (anti-oracle tests in `FieldProtectionMigrationTests`). The worker decrypts only values of the field named by the command, record by record, and writes them into the signed candidate it stages — it never returns plaintext to a caller. |

## 3. Authorization model

| Actor | May do |
|---|---|
| Organization owner / system administrator | Publish the organization policy (`PUT /organization/security-policy` → `UpdateMandatoryPolicy`); declassify (`ReclassifyField`); release Public/Internal fields; cancel a release; retry a failed decrypt migration. |
| Second organization owner / system administrator (distinct authority user) | Release a field that was recorded Confidential/Restricted, within 24 h of the declassification. |
| Form Designer | See protection state and progress; strengthen; retry failed **encrypt** migrations. Cannot request, approve, start, cancel or retry a release. |
| Record owner / contributor | Unaffected: reads and edits continue through the same authority decisions; an edit racing the cutover is refused with `FIELD_PROTECTION_CHANGED` and succeeds on retry under the new mode. |
| Business API runtime / worker | Submit deprotection/reprotection operations under the effective command only. |
| Business DBA | Cannot create, promote or complete a migration; forged rows do not change the status claim; a corrupted ciphertext fails its record (quarantined by the authority) and the field is never reported fully plaintext. |
| Another organization | 404 on every route; the authority refuses its commands against foreign resources. |

**Not available yet (documented residual):** PB-08 step-up (fresh FIDO2) assurance for these commands — the identity layer does not implement it; the commands rely on the session's authenticated principal and the distinct-principal rule. This is a production requirement, not waived.

## 4. State machine (as implemented)

```
Encrypted (requirement active)
  ──(owner/admin: ReclassifyField, approval ref)──► Encrypted, declassified (field_reclassification active, 24 h)
  ──(owner/admin [distinct for sensitive]: PublishFormSecurityRevision(Standard) Effective = CUTOVER)──►
Released (field Standard; barrier: no encrypted row of the field commits) + Decrypt migration Queued
  Queued ──(lease)──► Running ──► Completed + Verified (0 encrypted rows in authority-accepted heads) ──► "Fully migrated to plaintext · verified"
  Running ──(dependency down)──► Blocked ──(auto)──► Running
  Running ──(bounded attempts exhausted)──► Failed ──(administrator retry)──► Queued
  Queued/Running/Blocked/Failed/Completed ──(cancel-downgrade: PublishFormSecurityRevision(ApplicationEncrypted))──► Cancelled + rollback Encrypt migration ──► Encrypted · verified
```

Ordering guarantees: (1) the barrier flips atomically with the command (authority transaction) — there is no window in which both an encrypted and a plaintext row of the field can be accepted; (2) each record conversion is one accepted content revision, a concurrent user commit wins and the worker re-reads; (3) `Completed` is written only after the post-check; (4) cancellation never deletes rows; plaintext revisions written during the exposure window stay immutable history and are named in the audit event.

## 5. Risks accepted with this amendment

| Risk | Mitigation / residual |
|---|---|
| Plaintext persists in WAL, backups, replicas and immutable history after a later re-encryption. | Exposure window recorded per cancellation; purge of historic plaintext revisions is the retention/purge workflow (CLAUDE.md §4A), **not** promised here. |
| Low-cardinality values become inferable to a DBA once plaintext. | The owner's policy statement must acknowledge DBA readability; the policy switch is separate from the plaintext-Internal switch. |
| A compromised worker could write a wrong plaintext for a value. | Worker self-check (decrypt → re-encode → format-compare); the authority accepts only same-item pairs; residual trust in the business runtime as for every user write. |
| Downgrade used to make Confidential data readable without governance. | Reclassification by an administrator with an approval reference + release by a distinct administrator within 24 h; both journaled; a designer cannot do either. |
| Policy withdrawn during a running migration. | The command bound the policy at acceptance; a withdrawn policy refuses new releases (tested) — a running migration completes the already accepted release; cancel-downgrade is available. |
| No step-up assurance on the commands. | Residual until PB-08 is implemented; recorded in §3. |

## 6. Verification (local Docker stack, 2026-10-19)

`tests/integration/EnterpriseForms.StageBTests/Tests/FieldProtectionDowngradeTests.cs` (6 tests): policy gate and roles (designer/clerk/reader/other tenant/strengthen route/stale revision/wrong field kinds); full Internal release (barrier flip, 6 records decrypted through the authority, verified completion, values readable, reader denied, v1 unchanged, audit without values, re-strengthening afterwards); two-person Confidential release (same principal refused by the authority, distinct administrator accepted, reclassification consumed); concurrent writers across the cutover with a worker restart; interrupted (authority paused) and tampered ciphertext (record fails, forged completion ignored, administrator-only retry); cancellation with rollback re-encryption and exposure-window audit. Authority unit tests: planner (policy/roles/distinct principal/freshness/target/withdrawn policy) and rules (decrypt direction; barrier). Browser: `src/frontend/e2e/encryption-downgrade.spec.ts`. Results: `docs/STAGE_B_STATUS.md` §4 and `docs/evidence/stage-b/2026-10-19-encryption-downgrade/`.

## 7. What this amendment does not grant

Independent cryptographic/security review, managed key custody (Azure Key Vault / Managed HSM), Azure staging evidence, Level 2 production approval, PB-08 step-up assurance, purge of historical plaintext, or any production-readiness claim. These remain open in `docs/STAGE_B_STATUS.md` §7.
